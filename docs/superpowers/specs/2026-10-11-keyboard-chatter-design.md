# Keyboard chatter detector design

## Purpose and scope

Build a Rust terminal program for Windows, macOS, and Linux that monitors keyboard
input across applications, detects suspected keyboard chatter, and permanently
records each detected occurrence on the local filesystem. A symptom is a pair of
distinct presses of the same physical key whose press-to-press interval falls
inside a configurable range. Detection identifies a symptom; intentional rapid
double presses can meet the same rule.

The program must observe input without suppressing or modifying normal keyboard
operation. It stores detected symptoms, rather than a transcript of all input.
A desktop interface, automatic startup, remote storage, and input correction are
outside this version's scope.

## User requirements

1. Receive global keyboard events across applications.
2. Detect two distinct presses of the same physical key within a configurable
   time range.
3. Record every detected symptom with timestamps, key identity, interval, and
   relevant diagnostic metadata.
4. Store those records on the filesystem and preserve them across program exits
   and restarts. RAM-only storage does not satisfy this requirement.
5. Exclude automatic inputs generated by holding a key. They are not distinct
   physical presses and must never participate in detection.
6. Support Windows, macOS, and Linux with a terminal interface.

## Command line and defaults

The executable is named `bg-key-dbclk-checker`. It accepts `--min-ms`, `--max-ms`,
and `--output`. The default detection interval is 0 through 80 milliseconds,
inclusive. Both bounds must be finite and nonnegative, the maximum must be
positive, and the minimum must not exceed the maximum. Fractional milliseconds
are supported.

`--output` selects a JSONL file. Without it, the file is
`bg-key-dbclk-checker/symptoms.jsonl` under the operating system's local user data
directory: `%LOCALAPPDATA%` on Windows, `~/Library/Application Support` on macOS,
and `$XDG_DATA_HOME` or `~/.local/share` on Linux. The program creates missing
parent directories and displays the resolved location and detection range at
startup.

The terminal shows a short line for each saved symptom. Ctrl+C stops the program
and closes capture and storage cleanly. Monitoring runs while the process is
running; it does not install an operating system service.

## Capture architecture

Separate the platform-specific capture adapters, shared detector, append-only
storage, and command-line entry point. An adapter produces normalized events
with physical key identity, press/release/repeat classification, a monotonic
timestamp, and a wall-clock timestamp. Key identity uses scan codes or native
physical key codes rather than typed characters, so Shift, Caps Lock, and layout
changes do not turn one key into multiple identities.

Native capture is preferred over an application-focus listener or a generic
X11-only library. An application-focus listener would miss other applications;
an X11-only library would not cover Linux Wayland sessions.

- Windows uses background Raw Input keyboard events and a message loop. Use
  device identity and scan-code extension flags to distinguish keyboards and
  physical keys. Standard injected text through `SendInput` is outside this
  hardware input stream.
- macOS uses a listen-only keyboard event tap. Discard events marked as
  autorepeat and software-posted events where the operating system exposes that
  classification. Physical keyboard identity is not exposed by this API, so
  the source is the combined keyboard stream.
- Linux reads keyboard evdev devices without grabbing them. This works under
  X11 and Wayland. Classify kernel repeat events explicitly, retain each device's
  identity, and exclude virtual input devices by default. Include newly attached
  accessible keyboards while monitoring.

Use operating system key state at startup where available so a key held before
monitoring begins is not mistaken for a new press. A device disconnect, dropped
event stream, or capture restart invalidates the affected held-key and timing
state; do not compare presses across an input gap.

The adapters observe input that their operating system presents as keyboard
events. They cannot certify hardware authenticity for a device or driver that
presents synthetic events as hardware. Secure input modes and inaccessible input
devices also limit what an operating system permits an observer to receive.

## Detection rules

Maintain state independently for each source and physical key: whether it is
held and the most recent accepted press. Other keys pressed in between do not
erase that key's history. On macOS, source identity is the combined stream.

1. An explicit repeat event is ignored. It never updates press history or
   produces a symptom.
2. A press for a key already held is ignored for the same reason.
3. A release marks that key as no longer held. It does not create a symptom or
   replace its last accepted press.
4. A new press for a released key marks it held and compares its monotonic
   timestamp with its previous accepted press.
5. Emit a symptom exactly when the interval is inside the inclusive configured
   range. Always update the previous accepted press, including when its interval
   falls outside the range.

This means `press A, repeat A, repeat A` produces no symptom, even if the repeat
interval is inside the range. `press A, release A, press A` can produce a symptom.
Three distinct rapid presses produce two records, one for each adjacent pair.
Different keyboards do not form a pair where the capture API supplies separate
device identities.

Use monotonic time for interval calculation so a wall-clock adjustment cannot
change detection. Capture time at the input source, before storage work, so disk
latency does not determine the measured interval. Retain UTC wall-clock
timestamps for reading and comparing log records.

## Persistent records

Store one JSON object per line in an append-only UTF-8 JSONL file. Never truncate
an existing file when starting another monitoring session. Each record includes:

- schema version and a monitoring session identifier;
- the previous and current press timestamps in UTC;
- physical key code and a readable key name when available;
- operating system, input source, and device identifier/name when available;
- press-to-press interval in milliseconds;
- the minimum and maximum detection bounds used for that occurrence.

Write a complete line, flush any userspace buffer, and sync the file to disk for
each symptom before printing its saved notification. Create the file before
starting capture, and persist its directory entry when the platform permits it.
Logs remain on the filesystem until the user removes them; there is no automatic
expiration or rotation.

On an output creation, write, flush, or sync error, display a clear error and
stop with a nonzero exit status. Never continue claiming records were saved.
When appending to a file with a nonempty unterminated final line, refuse startup
with an explanation so a previous interrupted write cannot silently corrupt a
new record. Existing complete records remain intact.

## Permissions and capture errors

macOS requires the relevant Input Monitoring/Accessibility permission. Linux
requires read access to the keyboard event devices. Startup failures must
identify the missing permission and provide platform-specific instructions.
Do not silently fall back to capturing only terminal input.

If some Linux keyboards are inaccessible, explain which devices were skipped
and that capture coverage is partial. If no keyboards are accessible, stop with
an actionable error. Unexpected capture failure stops the application after
reporting the error; already-synced records remain available.

## Verification

Test the shared detector with deterministic event streams covering inclusive
timing bounds, fractional milliseconds, presses outside the range, intervening
keys, separate devices, rapid triples, explicit autorepeat, duplicate key-down
events, a key held before startup, release handling, input gaps, and wall-clock
adjustments.

Test real filesystem persistence: records parse as JSONL, survive closing and
reopening the writer, retain their original contents when another session
appends, and expose all required diagnostic fields. Verify invalid output paths,
write failures, and an incomplete trailing record cause errors instead of a
saved notification.

Test argument validation and help output. Add build/test CI for Windows, macOS,
and Linux. Hardware capture requires manual checks on each operating system:
type deliberate rapid double presses, hold a key, use modifier combinations,
switch application focus, attach another keyboard where supported, and restart
the program to confirm previously saved symptoms remain readable.
